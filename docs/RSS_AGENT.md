# RSS価値観スライド実験

Issueの本人コメントは、[原典アーカイブ](../sources/github-issues-001/README.md)へ文脈付きで保存します。最終稿・承諾・投稿の履歴とは別です。賛成・批評・質問もそのまま残り、Closeやタグ付けは不要です。保存しただけで次回の生成へ反映されるわけではありません。

この機能は、RSSから集めた話題へ既存の判断条件を仮適用し、本人確認前の投稿案をGitHub Issueへ作ります。政治・社会枠は過去実績のない領域なので、本人の意見を再現したものではなく、ゼロショット仮説として扱います。

## 構成

- `.github/workflows/rss_ai_agent.yml`：6時間ごとの収集、Geminiによる構造化、Issue作成。
- `config/rss_sources.json`：通常枠と実験枠のソース、配信元許可リスト、除外語。
- `tools/rss_agent.py`：RSS/Atom解析、配信元照合、重複排除、ノイズ候補除外。
- `prompts/rss_value_slide.md`：価値観スライド用の制約付きプロンプト。
- `tools/generate_rss_issues.py`：GeminiのJSON出力を、本人確認用Issueへ変換。
- `.github/workflows/import_rss_feedback.yml`：本人の本文コメントと後からの投稿報告を取り込む。クローズも互換トリガーとして残す。
- `tools/import_issue_feedback.py`：本人コメント、本文ハッシュ、固定書式を検証する。

## ソースについて

2026年10月23日の本人指示により、既知の興味に合う話題の推薦から、広い題材への本人反応を集める運用へ拡張しました。科学・宇宙、医療・健康、教育、環境・生き物、文化・芸術、スポーツ、暮らし・食・旅、仕事・福祉、司法・権利、交通・街・防災、経済・企業、一般、政治、世界、技術、ゲーム、公的情報の17分野を対象にします。アトリエ専用・GitHub Actions/Cursor専用の検索は休止し、ゲーム・技術全般の広域検索へ置き換えています。

Google News検索は各分野の広いキーワードを使い、新聞・放送局・通信社と分野別の媒体・公的機関の配信元名を許可リストで照合します。政治・世界の既存ソースは維持し、BBC日本語の直接RSSとe-Govも併用します。新しい分野も互換性のため `experimental-politics` トラックに置きますが、政治的な立場を意味しません。`news-science` 等のカテゴリラベルと、日本語のIssue見出しで区別します。

配信元名は空白・英字の大小を整えて完全一致で確認します。「共同通信」という許可名だけで「共同通信PRワイヤー」も通すことはしません。媒体名の別表記を許可する場合は、明示的に登録します。これはRSSメタデータの照合であり、運営主体の真正性や記事内容の独立検証ではありません。

2026年10月20日の実取得では、NHKの旧直接RSSは応答しても記事更新が8月で止まっていたため無効化し、現在のNHK記事をGoogle News経由で取得しています。旧共同通信検索も配信元が47NEWSやYahoo等になって原配信を確認できなかったため無効化しました。配信元の許可リストを緩めて代用することはしません。状態は `enabled` と `disabled_reason` に記録しています。

候補は、既存RSS Issueのカテゴリラベルと作成日時を調べ、未出の分野、その次に最も長く出ていない分野を優先して選びます。開閉済みの両方を集計し、単にコメントされた時刻では優先順を変えません。1回6件より分野数が多くても、次の実行では出ていない分野へ順番が回ります。同一カテゴリ内もソースを一巡し、各ソース内は新着優先です。候補がない分野の枠はほかへ回します。頻度は引き続き6時間ごと、既定6件です。

これは既知の好みに基づく選別ではありません。「知らない」「興味を持てない」「判断できない」も有用な本人の反応です。原典コメントを第三段階で文脈とともに読む対象にし、作文や具体的な賛否を毎回求めるものではありません。生成側にも、未知の題材を無理に制度批判へ変換せず、材料不足なら保留する指示を加えています。保存だけでモデル学習や生成への反映が完了するわけではありません。

最大7日前までの記事を対象とし、株価一覧・銘柄プロフィール等の非記事タイトルを除外します。日付不明は不明のまま扱います。生成前に、開閉済みを含む既存RSS Issueの候補IDを除外するため、同じ候補が先頭枠を占め続けたり、その生成でAPIを消費したりしません。別タイトル・別URLで同じ出来事を扱う記事すべてを意味的に重複排除する仕組みではありません。

取得件数・除外件数・エラーは収集JSONの `source_diagnostics` と `errors`、各分野の直近出題日時は `category_last_issued_at`、選択分野はActionsの実行サマリーで確認できます。RSSの可用性やGoogle検索結果は変わるため、各分野のIssueが毎回必ず出る保証や、全世界のあらゆる出来事の網羅を意味しません。

Google Newsは配信経路であって事実の保証者ではありません。実験枠ではRSS内の配信元名を許可リストと照合しますが、タイトルと概要だけで記事内容の正確さや「純粋な事実」を保証することはできません。そのため、全候補を `fact_candidate_not_verified` としてIssueへ載せ、原記事・一次資料で未確認の点を別欄へ出します。

除外語は「批判殺到」「コラム」など明白な候補を減らす補助です。感情語がない記事を客観報道と断定する分類器ではありません。LLMによる事実候補の抽出も、事実確認の代替にはしません。

官報や法案の直接フィードを追加する場合は、運営主体とURLを手動で確認してから `config/rss_sources.json` へ追加します。存在を確認できないRSS URLを推測で登録しません。

## GitHub設定

リポジトリのActions Secretsへ次を登録します。

- `GEMINI_API_KEY`：RSS断片の構造化と初稿生成に使用。

必要ならActions Variablesへ `GEMINI_MODEL` を設定します。未設定時は `auto` とし、そのAPIキーで利用可能な `generateContent` 対応テキストモデルを取得して、Flash系の安定版を優先選択します。固定名を設定した場合は自動フォールバックしません。`GITHUB_TOKEN` はActionsが発行する標準トークンを使い、個人アクセストークンをSecretsへ追加する必要はありません。

リポジトリまたはOrganizationのActions設定で、Workflowの読み書き権限とIssue作成を許可してください。収集ワークフローは `contents: read` と `issues: write` だけを持ちます。履歴書込ワークフローだけが `contents: write` を持ち、GeminiのSecretは受け取りません。

ブランチ保護でActionsからmainへ直接pushできない場合、フィードバック取込は失敗します。その場合はbot用ブランチとPull Requestを作る運用へ変更してください。保護を迂回する設定は推奨しません。

## スマホでの操作

1. 初稿をコピーし、必要なら修整して、その確定文を本人アカウントから**そのままコメント**します。タグもコードブロックも不要です。
2. コメントを合図に取り込みます。IssueをCloseする必要はありません。初稿をそのまま使う場合も、その全文をコメントしてください。
3. 実際に投稿したら、別コメントで **「投稿しました」** と知らせてください。「投稿したよ」「投稿済みです」「Xに投稿しました」も受け付けます。Xの投稿URLを添えるか、URLだけの別コメントでも構いません。

「上記のコメントで投稿しました。」「この本文を投稿しました。」「上記投稿しました」「上記X投稿しました。」「上記、投稿しました。」のように直前の本文を指す報告も受け付けます。これは新しい投稿本文にはしません。ニュース記事の出典URLと、実際の投稿URLは区別します。

確定文と投稿報告は別コメントにしてください。通常の本人コメントは確定文として扱うので、本文そのものを貼ってください。短い挨拶・了承や「まだ投稿していません」は取り込みません。複雑な相談・補足はこのチャットで行うと、最終本文との混同を避けられます。

本文コメントのみなら本人承認済み・投稿報告なしとして記録します。後から投稿報告が届けば、同じ記録へ実投稿の本人申告を追記します。URLがなくてもIssueコメントを申告の参照先として残します。外部の表示内容を取得・独立検証したという意味ではありません。

本文の修整は元コメントの編集、または新しい全文コメントで受け付けます。過去の本文と投稿履歴を削除せず、新しい修整として追記します。修整前の投稿報告を、修整後の本文が投稿された証拠として再利用しません。新しい本文を投稿した場合は改めて報告してください。

Issueのクローズは整理のため任意です。閉じた後の投稿報告コメントも取り込みます。同じコメントやクローズ通知の再実行では二重登録しません。旧来の `/final` とコードブロック、同じコメント内の `/posted URL` も引き続き読めます。

取込には次を確認します。

- Issueに `rss-agent` ラベルがある。
- Issue本文の候補ID、初稿、初稿ハッシュが一致する。
- コメント投稿者・実行のきっかけを作ったアカウントがリポジトリ所有者本人である。
- 本文と承諾、投稿報告のハッシュ関係が正しい。

これは手動コピー用の校正履歴です。コメントを外部SNSへの自動投稿の許可として扱いません。

## ローカル検証

ネットワークを使わない単体テストと履歴検証は次で実行できます。

```bash
python3 -m unittest discover -s tests -v
python3 tools/validate.py
```

実際のRSS取得は、接続先の停止やレート制限で失敗する可能性があります。一つのフィードが失敗しても他のフィードは処理しますが、全フィードが失敗して候補がゼロの場合はWorkflowを失敗させます。
