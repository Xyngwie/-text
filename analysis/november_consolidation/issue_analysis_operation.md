# Issue原典の自動分析と、この窓での精読

Issue本文と本人コメントは、既存の `Archive owner Issue comments as source material` が保存する。新しい `Issue source classification and analysis proposals` は、その保存済み原典から未処理の本人本文・コメントを拾い、分類と分析案を作る。

## 実行

毎時53分に最大5件。手動実行では1〜10件を指定できる。原典保管の定期実行は毎時43分なので、その後を選んだ。Actionsの実行時刻は遅れる場合があり、保管処理の完了を直接保証するトリガーではない。次の巡回でも取り込める。

- Secretは既存の `GEMINI_API_KEY` を使用する。
- モデルはリポジトリ変数 `ISSUE_ANALYSIS_MODEL`、未設定なら既存処理と同じ自動選択。
- リポジトリ変数 `ISSUE_ANALYSIS_PAUSED=true` でこのActionを停止できる。
- 対象がなければAPIキーを要求せず、生成APIを呼ばず終了する。スケジュール自体は新規原典を検出するため残る。

## 対象と更新

保存済み原典の最新スナップショットを使う。本人が書いたIssue本文と、本人のコメントを対象にする。開閉状態は問わない。PR、他人のコメント、空本文は分類対象にしない。他人やAIの文は文脈として読まれうるが、そのまま本人の文章にしない。

精査済みの本文ハッシュは自動処理しない。AI処理済みでも、本文またはIssue全体の文脈が変われば、新しい原典ハッシュで再処理する。同じ本文・文脈は繰り返さない。過去のAI案は保存されるので、現在の件数は最新スナップショットに一致する案で数える。

完全なIssue文脈と対象本文が入力予算に収まる範囲で処理する。大きすぎる資料を黙って省略しない。収まらないものは結果の `blocked_unit_ids` に出して精読待ちに残す。API失敗や不正な引用・出力で未処理を処理済みにはしない。

## 出力

- `data/issue_ai_reviews.jsonl`：原典ID・本文/スナップショットのハッシュ・分類案・分析案・モデル/実行記録。
- `batches/issues/auto/IA-*.json`：バッチごとの構造化レポート。
- 同じ名前の `.md`：窓で精読するための引用・分析案・留保の読みやすいレポート。
- ActionのSummary：処理件数、残数、対象ID、レポートの場所。

RSS初稿との文字列比較はコードで行い、原文・差分を保持する。モデルが出した分類や分析案の根拠引用は、対象本文との一致を検証する。機械的な差分は意味の正しさを保証しないし、引用が一致するだけで仮説が正しいことにもならない。

自動案は `ai_proposed_pending_close_reading` とし、精査済み台帳 `data/issue_reviews.jsonl` とは別に保持する。新しいIssueの起票やコメント送信は行わない。

## この窓で行うこと

窓ではレポートと原典を精読し、作者の区別、採用と許容、指摘の射程、別事例との関係を確かめる。確定できた分類のみ精査済み台帳へ記録し、必要なら正式な分析へ統合する。

コピペ・修整した本文は採用原稿。評価・却下コメントはその原稿への反応。投稿した旨の報告は本人申告の実投稿。自動案はこれらを分類候補として示すが、公開承認や投稿履歴の変更には使わない。許容された表現から本人の理想の口調を自動学習したことにもならない。

既存の投稿原稿取り込みでは、精査済みの評価コメントだけを正確な本文ハッシュで除外する仕組みを使う。今回のAI分類案はそこへ自動投入しない。これによりAIの誤分類が本人の採用原稿を消したり、評価コメントを承認したりする経路を作らない。

## ローカルで確認

```sh
python3 tools/analyze_issue_batch.py --dry-run
python3 -m unittest discover -s tests -p 'test_issue_analysis.py'
python3 tools/validate.py
```

`--dry-run` はAPIを呼ばず、対象・未処理件数・大きすぎる原典を確認する。GitHub側の実生成はActionsで確認できる。
